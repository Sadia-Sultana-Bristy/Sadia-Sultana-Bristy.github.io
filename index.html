About

I’m the tester who reads the rating rules before opening the app.

Insurance software is unforgiving. A missed state rule or a rounding error in a premium becomes a compliance issue or an incorrect bill. I learned to test this domain by following the money and the data. I trace a policy from quote to bind to claim, then confirm in the API and the database that every number and flag landed where it should.

My foundation is careful manual testing: functional, regression, smoke, integration, end-to-end and UAT. I write test cases from requirements, not from screens. I work closely with client stakeholders on scope, and I write bug reports that developers can reproduce on the first try.

I started automating where it paid off most. Playwright regression scripts in JavaScript now cover the repetitive checks, which frees each sprint’s testing time for the edge cases that actually find bugs. I’m growing deliberately in that direction: broader automation coverage, API test suites and CI pipelines.

How I test a release

The same five steps, whether it’s a single feature or a full policy lifecycle.

  1. Read the requirements

    Business rules, rating tables and acceptance criteria come first. I clarify scope with stakeholders before writing a single case.

  2. Design the scenarios

    I build test matrices that cover the happy path, state-by-state variations, boundary values and the edge cases people forget.

  3. Test every layer

    I check the UI, the API in Postman or Swagger, and the database with SQL, so a bug can’t hide behind a correct-looking screen.

  4. Report so it gets fixed

    Jira tickets include exact steps, expected and actual results, and evidence. I stay with each defect until the fix is verified.

  5. Protect what already works

    Regression and smoke passes run before sign-off. The repetitive parts run in Playwright.
